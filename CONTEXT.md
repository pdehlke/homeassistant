# Home Assistant Buildout

This context covers pde's Home Assistant instance and everything that touches it: the native
dashboards, the Homie Dashboard fork, and the Crestron, Rachio, Lennox, Music Assistant, Harmony
Hub, EV charger, and networking subsystems it integrates. Single context for the whole repo, per
[docs/agents/domain.md](./docs/agents/domain.md).

## Language

### Home Assistant structure

**Area**:
A room or space in this instance's HA registry. Belongs to at most one Floor; areas cannot nest.
_Avoid_: room (use Area for the registry concept, "room" only in plain prose).

**Floor**:
The only registry level above Area. Used here purely to express containment (e.g. Garage is
modeled as its own Floor holding the Garage and Garage Mechanical Closet areas), not to represent
an actual building storey.
_Avoid_: story, level (in this HA-registry sense).

**Mechanical Closet**:
A physical equipment space, always its own Area, kept separate from the room its thermostat or
fixtures sit in (e.g. North Mechanical Closet, Garage Mechanical Closet).

**Template light**:
This instance's stand-in for real lighting control before Crestron integration lands: an
`input_boolean` + `input_number` + Template Helper `light.*` entity, built entirely via config
flow so the entity ID survives the later swap to real Crestron-driven control unchanged.

### Native dashboards

**Home** (`vision-sample`) / **Tablet Home** (`tablet-home`) / **Standalone domain dashboard**
(e.g. `dashboard-lights`):
Retired 2026-08-16. Home was a tabbed kiosk dashboard; Tablet Home was the root dashboard it
replaced; the standalone domain dashboards (Lights, A/V, Alarm, Climate/Lennox Home) were Home's
independently-regenerated counterparts. All deleted, along with the `Tablet` HA user, in favor of
Homie Dashboard as the sole kiosk target. See
[native-dashboards-retired.md](docs/native-dashboards/native-dashboards-retired.md) and ADR-0062.
_Avoid_: don't read any of these three as live — check the retrospective doc before assuming
current behavior from old cross-references.

**Overview**:
The sidebar's separate, HA-built-in dashboard generated by the `home` Lovelace strategy (one view
per area). Its `url_path` happens to be `home`. Unrelated to the retired Home dashboard above and
to Homie Dashboard's Overview A/B/C below — the naming collision is real and confirmed, not a
documentation error.
_Avoid_: don't read "Overview" alone as shorthand for Overview A/B/C.

**`kiosk_mode`**:
Per-dashboard, per-user HACS frontend config (`hide_header`/`hide_sidebar`) hiding HA's own
chrome. `homie-dash` and `dashboard-office` both hide header and sidebar for their respective
kiosk users (`Homie Dashboard`, `Office`). The now-retired Home dashboard was the one exception:
it hid only its sidebar, since its native tab strip was its only navigation.

**visionos**:
The active Lovelace theme (`Nezz/homeassistant-visionos-theme`), with a glass-blur card style.
Early docs called it the "Frosted Glass theme" before its technical name was established; that was
a nickname, not a different theme that was later replaced.
_Avoid_: Frosted Glass (early nickname, not a distinct theme).

### Homie Dashboard

**Homie Dashboard / Homie Dash / Homie**:
The third-party Lovelace dashboard (fork of `Big-Edge2297/homie-dashboard`, tracked at
`pdehlke/homie-dashboard`) deployed via HACS as an iframe-strategy dashboard (`homie-dash`).
"Homie Dashboard" is the product/account name, "Homie Dash" is the dashboard's title/slug, "Homie"
is casual shorthand for all of it. This CONTEXT.md is the only place this fork's UI vocabulary is
written down; the fork's own repo has no glossary of its own yet.

**Homie Dashboard (HA user)**:
A dedicated non-admin HA account (username `homie`) that Homie's own WebSocket connection
authenticates as, holding a long-lived token embedded in `config.js`. Same name as the product
above but a distinct thing: one account, not the software.

**Tablet (HA user)**:
Retired 2026-08-16 along with the Home dashboard it was built for; deleted, not just dormant. Not
the same account as Homie Dashboard, which is what the physical wall tablet actually runs now.

**Overview A / Overview B / Overview C**:
Three distinct full-screen views inside Homie Dashboard. Overview A is the primary chip-based
screen; Overview B mirrors Overview A's rendered center grid and sidebar list without
recomputing; Overview C is a structurally different layout (Solar, Garden/Irrigation, Main
House/floors columns, its own icon sidebar). Before Overview B/C existed, Overview A was called
"Screen A" — the regression test file `test/screen-a.test.cjs` still carries that name.
_Avoid_: Screen A (legacy name for Overview A), bare "Overview" (see Native Dashboards' entry).

**Chip**:
A labeled control button in Homie's bottom control row (Lights, Climate, A/V, Irrigation, Scenes,
Music, TV, NAS). Shows a live on/off glow and sometimes an "N on" count or an alert dot; tapping
opens the chip's overlay. NAS is the only chip restricted to admin viewers; see `isAdminViewer`
below.

**`isAdminViewer`**:
The live, per-viewer identity check gating the NAS chip's visibility: reads the real logged-in HA
user's admin flag off the parent frame (same same-origin cross-frame access as the Climate
overlay's native dialog), fails closed (hidden) on any uncertainty. Not a device-level Settings
toggle — deliberately tied to who's actually looking, not which browser they're using. See
[homie-nas-chip.md](docs/homie-dashboard/homie-nas-chip.md).

**Bubble**:
A round icon button inside a chip's overlay: one per scene (Scenes chip), or one per Station or
Playlist (Music chip). Nested inside a chip, not the same thing as one.
_Avoid_: don't call the Music chip's "All Off" row a bubble; it's a static action row sitting
alongside the Stations/Playlists category rows, not a round icon inside an expanded category.

**Overlay**:
The panel a chip opens on tap, hand-rolled by Homie itself.
_Avoid_: don't use "overlay" for Home Assistant's native more-info component — that's "dialog."

**Dialog**:
Reserved specifically for Home Assistant's own native more-info dialog (`ha-more-info-dialog`),
opened via the `hass-more-info` event that Homie's iframe (same-origin with the HA frontend) can
dispatch directly. Never used for Homie's own hand-rolled UI.

**Picker**:
The Main House / Office Wing two-button chooser Homie shows when the unfiltered Climate chip is
tapped, before opening the native dialog for whichever room is picked.

**Glow**:
Shared visual language for "on" state across chips, bubbles, and Overview C's sidebar icons: a
lit/brightened treatment (accent-colored ring or brightened icon/label) driven by the same live
on-state logic that feeds each control's "N on" count.

**Sidebar (Overview C)**:
Overview C's own dynamic left-side control list, each entry deriving its icon from the underlying
entity domain (with overrides for Scenes/Music, which have no matching HA domain).
_Avoid_: don't confuse with Home Assistant's own navigation sidebar, which `kiosk_mode` hides
separately.

**Alert indicator / alert triangle / red-dot** (Homie):
Bottom-left (Overview A/B) or sidebar (Overview C) warning icon, lit when any HA
`persistent_notification` is pending; on Climate specifically, also lit by a Lennox thermostat's
alert severity reaching moderate or critical.

**Pill**:
A compact multi-value stat readout, e.g. the three-value Solar pill (generation, whole-house load,
grid-flow direction).

**Scene** (Homie sense):
A bottom-row bubble backed by one or more real HA `scene.*` entities, given a synthetic on/off
state HA's own scenes don't have: on if any entity the scene controls is currently on. Toggling
off turns those entities off directly, since HA scenes have no reverse action of their own.
_Avoid_: don't conflate with the stock HA `scene.*` entity, which carries no on/off state of its
own, only a last-activated timestamp.

**Station**:
A Music chip bubble representing one pre-configured Music Assistant radio stream (a
`library://radio/<n>` URI), not an HA entity in its own right. Lives under the Music chip's
"Stations" accordion category. All seven target the single fixed player `media_player.crestron`.
_Avoid_: don't use "station" for a Playlist bubble; they're a different URI scheme and a different
on-state mechanism (see Playlist).

**Playlist** (Homie sense):
A Music chip bubble representing one Music Assistant library playlist (a `library://playlist/<n>`
URI), sourced from a Jellyfin playlist that MA has ingested into its own library, not a raw
Jellyfin API call. Lives under the Music chip's "Playlists" accordion category, alongside but
distinct from Station. Always plays shuffled; a Station always plays unshuffled, and starting one
turns shuffle back off regardless of what a prior Playlist tap left it as. Its on state can't be
read the way a Station's can: Music Assistant rewrites the player's `media_content_id` to the
current track's own URI the moment a playlist starts, never the playlist's URI again, so Homie
tracks "this bubble is the one that's on" in memory instead of matching live state.
_Avoid_: don't conflate with the stock HA `scene.*`-adjacent "Scene" (Homie sense) above; a
Playlist has no synthetic derived state at all, only this tracked marker.

**Floors card**:
A card on Overview C with one face per floor/zone (Main House, Office Wing), each with an expand
button (opens the Climate dialog filtered to that floor) and a stat grid (temp/target,
humidity/PM2.5).

**Launcher**:
A now-removed standalone card ("Main House thermostat launcher"), superseded by the floors card's
own expand button.

**`HOMIE_ASSET_VERSION` / cache-busting `?v=`**:
Homie's two-boundary cache-busting convention: a version token bumped in `homie-dashboard.html`
whenever any nested asset's bytes change, mirrored in the `homie-dash` Lovelace iframe's own `?v=`
query parameter.

**`config.js` / `homie-custom.js` / `homie-dashboard.html`**:
The three live files under `/config/www/community/homie-dashboard/`. `config.js` holds
house-specific config, including the real HA token; `homie-custom.js` holds pde's non-upstream
patch behavior; `homie-dashboard.html` is upstream markup/CSS/JS, patched in place.

### Crestron system

**MC2E**:
Crestron control processor; Cresnet bus master for the CNX-B8 keypads and CLX lighting modules,
and IP master of the Ethernet link to AADS.

**AADS** (Adagio Audio Distribution System):
Amp/matrix/tuner hardware with its own onboard 2-Series control engine; owns the ST-IO's Cresnet
leg, the four TSW-752 panels, and (currently) the Apex alarm system's RS-232 connection.

**CP3N**:
Fallback control processor that would fully replace MC2E as Cresnet master and HA XSIG host, used
only if MC2E fails the documented suitability tests.

**CLX lighting modules** (CLX-1DIM8, CLX-1DIM4, CLX-4HSW4):
Cresnet dimmer/switch modules driving the Garage rack's lighting circuits.

**CNX-B8**:
The wall keypad model (8 labeled buttons) used throughout the house for lighting control; 9 units
across 7 rooms.
_Avoid_: wall plate (an earlier, less precise name for the same device).

**TSW-752**:
Crestron touch panel model, 4 units, registered to AADS over Ethernet.

**ST-IO**:
A Cresnet I/O expansion module (8 relay outputs, 4 analog/digital inputs) on AADS's Cresnet leg,
suspected to interface with the alarm system; exact wiring unconfirmed.

**Cresnet**:
Crestron's proprietary RS-485 bus (38,400 baud) connecting MC2E to the CNX-B8 keypads and CLX
modules. Frame-level protocol is undocumented; only the physical layer is public.

**Cresnet bus master**:
Whichever processor owns/drives the Cresnet bus (currently MC2E).
_Avoid_: don't conflate with "IP master" below — both get called "master" informally, but they're
different roles.

**IP master**:
The processor that owns the Ethernet/CIP link between MC2E and AADS (currently MC2E).

**XSIG**:
Crestron's Intersystem Communications join protocol (digital/analog/serial joins) carried over
TCP — the transport a Home Assistant integration would use to talk to MC2E/CP3N.

**Ethernet Intersystem Communications (ISC)**:
The existing Crestron-to-Crestron Ethernet link between MC2E and AADS. Distinct from XSIG, which
is HA-facing, though [crestron-migration.md](./docs/crestron/crestron-migration.md) uses the two terms loosely together in places.

**Alarm keypad**:
The DSC-branded wall-mounted interface unit (faceplate visible in the pantry). A user-facing
keypad, not the alarm system itself.
_Avoid_: don't call this "the alarm panel" — that's a different component (see below); an earlier
doc used the two loosely and should be tightened.

**Alarm panel / Apex Destiny 6100**:
The actual alarm control system, integrated with Crestron via RS-232 into AADS. The thing any HA
arm/disarm/status integration would actually talk to.

**Path A**:
The near-term design for reaching HA-Crestron control: hire a programmer to add a scoped XSIG
join-mapping bridge to the existing MC2E, leaving the Cresnet bus, keypads, and processors
otherwise untouched. One of two speculative designs for the end state, not yet committed to.

**Path B**:
The alternative, deferred design: physically tap the Cresnet bus, reverse-engineer its frame
format, and build an HA-native bridge that removes MC2E and AADS from the lighting bus entirely.

**Path B spike**:
The concrete verification activity for Path B: tapping Cresnet at the Great Room CNX-B8 keypad's
pluggable connector with a USB-to-RS-485 dongle, tracked as GitHub issue #1.

**XSIG Programmer Scope (SOW)**:
A work-in-progress Statement of Work drafted to solicit bids from Crestron programming
contractors to execute Path A. Not itself a finalized architecture decision — where its draft
language touches open questions (e.g. where the alarm bridge ends up hosted), those questions
remain open, not settled by the SOW.
_Avoid_: don't read this document as having decided where the alarm bridge lives; that's a
standing open item (see Alarm bridge below).

**Alarm bridge (location)**:
Open item: whether the Apex alarm system's XSIG exposure ends up hosted on AADS (keeping it as the
alarm bridge) or moved to MC2E/CP3N. Not yet decided.

**REPORTCRESNET**:
A telnet console command on MC2E/AADS that enumerates devices on a Cresnet leg without physical
sniffing hardware — the method used for this instance's device inventory.

### Lennox / Climate

**iComfort S30 (North / South)**:
The two Lennox thermostats, integrated via the `lennoxs30` HACS integration in local mode,
confirmed to have no Crestron tie-in.

**Main House / Office Wing**:
Homie Dashboard's Climate-chip display labels for South and North respectively — a separate
naming domain from North/South, deliberately not unified with the entity-ID naming.

**`_alert` sensor**:
A Lennox thermostat's console-mirroring status field (`critical`/`moderate`/`minor`/`info`/
`none`). The trustworthy trigger for alerting.

**`_active_alerts` sensor**:
A separate, more granular Lennox field (count + structured alert list) that can lag or self-clear
independently of `_alert`. Used only as enrichment, never as a trigger.

### Rachio / Irrigation

**Main Irrigation**:
The hard-wired Rachio controller device owning the house's zone switches, standby mode, and
schedules.

**Back Yard Smart Hose Timer**:
A separate, battery-powered Rachio device with one valve, sharing the same Rachio config entry as
Main Irrigation but polled independently.

**Zone**:
A Main Irrigation-managed irrigation area, represented as a switch entity. Disabling one in the
Rachio app deletes its HA entity rather than flipping a state.

**Valve**:
Back Yard's single controllable unit — deliberately distinguished from "zone" even though tracked
by the same presence/absence detection mechanism.

**Standby mode**:
A controller-wide toggle pausing all scheduled watering at once; a real on/off entity, unlike
zones/valves, which simply disappear when disabled.

**Baseline-diff detection**:
This project's core disabled-zone/valve detection mechanism: compare a remembered set of entity
keys against the live set every run; anything missing gets reported once, then the baseline
self-heals by being overwritten.

**Red-dot indicator** (Rachio):
A live current-state entity pair answering "is anything disabled right now," distinct from the
baseline-diff's "did something change since last check."

**Periodic reload**:
An hourly forced reload of the Rachio config entry — the only mechanism that refreshes stale
zone-disable state on this instance absent a live config-change webhook.

### Music Assistant

**HOMEii Flow**:
The HACS Lovelace card (`custom:homeii-music-flow`) used for the Sound dashboard's Music Assistant
controls.

**Sendspin**:
HOMEii Flow's "play through this browser tab" feature; needs a Music Assistant token and is
blocked by Chrome's Local Network Access restriction over plain HTTP.

**`ma_token`**:
A Music Assistant long-lived access token, distinct from an HA token. Required for Sendspin and
artwork proxying.

**Provider mapping**:
The field on a Music Assistant library item (`provider_mappings[].provider_domain`) naming which
backend actually supplies it, e.g. `jellyfin` or `builtin`. Only visible through MA's own API
(`music/get_library_item` over the HA ingress WebSocket), not through the HA-side
`music_assistant.get_library` service, whose response schema has no provider field at all. This is
the one reliable way to tell a Jellyfin-sourced playlist apart from one of MA's own built-in smart
playlists; see [docs/homie-dashboard/homie-dynamic-playlists.md](docs/homie-dashboard/homie-dynamic-playlists.md).

### Harmony Hub

**Activity**:
Harmony's mode-switch concept (e.g. "Watch TV") — the only level of control `remote.harmony_hub`
supports. HA has no direct per-device command layer configured.

**TV chip**:
Homie Dashboard's control for the Harmony-driven living room A/V, including a volume/mute row
added on top of the existing activity switcher.

### EV Charger

**OpenEVSE**:
The Garage Level 2 EV charger, integrated via HA's official `openevse` integration.

**Divert**:
OpenEVSE's solar-surplus charging feature; read-only in HA, must be configured on the charger's
own web UI. A separate feature from load shaper below.

**Load shaper**:
A separate OpenEVSE current/load-management feature, reported via largely disabled-by-default
diagnostic entities.

### Hardware & hosting

**Raspberry Pi 4**:
The former host for this Home Assistant instance. Retired by the Proxmox migration below,
confirmed live 2026-08-24. _Avoid_: don't read this as the current host in any doc dated before
that migration — see below.

**Proxmox migration**:
Completed move of this instance from the Raspberry Pi 4 to a Late 2014 Mac mini, running
Proxmox VE rather than the bare-metal install originally planned.
[docs/hardware/mac-mini-migration.md](./docs/hardware/mac-mini-migration.md) is the original bare-metal plan, now superseded
and marked as such; [ADR-0063](docs/adr/0063-proxmox-virtualization-over-bare-metal.md) records why virtualization replaced
it (Jellyfin needed to run alongside Home Assistant, not instead of it). The full build procedure
lives in the sibling `pdehlke/proxmox` repo's `mac-mini-proxmox-plan.md`, not here.

**Caddy reverse proxy**:
A small LXC guest on the same Proxmox host that fronts Home Assistant, Music Assistant, and
Jellyfin, routing by hostname. Replaced direct `:8123`/`:8095` access, which no longer works at
all. Launched on plain HTTP port 80; automatic HTTPS (real Let's Encrypt certificates) went live
the same day, and plain HTTP now 308-redirects to HTTPS rather than serving directly. See
[docs/networking/caddy-reverse-proxy.md](./docs/networking/caddy-reverse-proxy.md) and
[ADR-0064](docs/adr/0064-caddy-reverse-proxy-replaces-direct-ports.md). _Avoid_: don't read `hass.ehlke.net`/`mass.ehlke.net`
with a port suffix as current; that was true only before 2026-08-24. Don't assume every downstream
`http://` reference updated itself when HTTPS went live. Music Assistant's own `base_url` setting
was still `http://` as of the last check; see caddy-reverse-proxy.md's "What's still open."

**HAOS**:
Home Assistant OS. Still the install method this instance runs, chosen originally for the
Supervisor and its add-on ingress, which Music Assistant depends on
([ADR-0052](docs/adr/0052-haos-bare-metal-over-container-supervised.md)). Runs as a VM under Proxmox VE now, not bare metal
on the host — a separate decision ([ADR-0063](docs/adr/0063-proxmox-virtualization-over-bare-metal.md)) layered on top, not a revision
of the HAOS-vs-Container/Supervised choice itself.

### Synology NAS

**Synology NAS dashboard**:
A live read-only Home Assistant dashboard for the current Synology appliance's health and capacity,
used primarily from the owner's authenticated desktop or mobile session. It was deployed on
2026-08-17 at `dashboard-nas` with Overview and Trends views. Homie Dashboard's own NAS chip
(admin-only, see [homie-nas-chip.md](docs/homie-dashboard/homie-nas-chip.md)) followed the same day,
reproducing the Overview's content, not the Trends charts.
_Avoid_: Storage dashboard, infrastructure dashboard (both imply a broader system boundary).

**NAS health summary**:
The single Home Assistant-owned interpretation of whether the Synology NAS needs attention,
implemented as `sensor.nas_health` and shared by the standalone dashboard and Homie Dashboard's NAS
chip. Its four states are Healthy, Attention, Critical, and Unknown.
_Avoid_: separate health calculations in each dashboard frontend.

**NAS health state**:
Healthy means all required evidence is present and within policy; Attention means a warning or
Security Advisor finding; Critical means a known integrity failure or critical threshold; Unknown
means required evidence is missing. Known Critical conditions outrank Unknown.

### Networking & remote access

**`hass.ehlke.net` / `mass.ehlke.net`**:
The real DNS names (resolving to the internal LAN address) used for all HA and Music Assistant
access, replacing the retired `.local` mDNS hostnames. Reached through the Caddy reverse proxy
since 2026-08-24; no port suffix. Proxy launched on plain HTTP, then automatic HTTPS (real Let's
Encrypt certificates) went live the same day; use `https://`, not `http://`, as current. Plain
HTTP now redirects rather than serving directly.
_Avoid_: `homeassistant.local`, `mass.local` (retired 2026-08-11), literal LAN IP addresses (a
since-retired workaround that caused a CORS bug), a `:8123`/`:8095` port suffix (retired
2026-08-24, see [Caddy reverse proxy](#hardware--hosting) above), `http://` as the current scheme
(superseded the same day by automatic HTTPS).

**Home Assistant Cloud / Nabu Casa / Remote UI**:
The paid remote-access service (`hass_nabucasa` package) exposing this instance externally via a
custom domain and managed TLS certificate.

**Trusted networks auto-login**:
The `trusted_networks` auth provider entry in `configuration.yaml` that logs the Office wall
display's Raspberry Pi in as the `office` user purely on its LAN address, with no credential on
the device. Depends on Home Assistant's trusted proxies list naming only the Caddy proxy, since a
client inside a trusted proxy range is refused. See
[trusted-networks-auto-login.md](docs/auth/trusted-networks-auto-login.md) and ADR-0065.
_Avoid_: reading it as a kiosk or dashboard feature; it decides identity only, not what is
displayed. The `kiosk_mode` block above is the separate, unrelated thing that hides HA's chrome
for the same account.
